# Issue v1.0.5 - RAGMaker: Fix Directory Nesting & Add Project Name Flow

## 前提知識
- docs/Architecture/Architecture.md
- docs/guidelines/descriptive_naming_guidelines.md
- .gemini/commands/rag.md

## 経緯
`ericbuess/claude-code-docs` をソースとしたナレッジベース構築において、以下の2点の利便性・整合性の問題が発覚した。
1. **ディレクトリの2重化**: インストール後の構造が `introduction/introduction/` のように、カテゴリ名が重複して入れ子になっていた。
2. **配置先の不明瞭さ**: `ask_dir` で選択したディレクトリ直下にファイルが展開され、プロジェクトごとの管理が困難であった。

## 現状の問題点
- `create_knowledge_base.py` が空のカテゴリディレクトリを事前に作成し、その後に `move_file` が `.tmp/cache/` 内の（カテゴリ分け済みの）コンテンツをコピーしていたため、フォルダ構造が重複した。
- `/rag` ワークフローにおいて、ユーザーが「どのプロジェクトとして保存するか」を明示的に決定するステップが欠落していた。

## ゴール（完了の定義）
- [x] `create_knowledge_base.py` がカテゴリディレクトリを自動作成しないよう修正されている。
- [x] `.gemini/commands/rag.md` において、プロジェクト名の確認ステップが追加されている。
- [x] プロジェクト全体の pytest を実行し、修正後の `create_knowledge_base` テストを含む全てのテストがパスしている。

## 解決策の概要
1. **ツール改修**: `create_knowledge_base.py` の役割を「外箱の作成（.geminiディレクトリ等の準備）」に限定し、カテゴリディレクトリの作成責務を削除。
2. **ワークフロー改修**: `rag.md` を修正し、`ask_dir` で得たベースパスに、ユーザーが指定したプロジェクト名を結合して最終的な `kb_root` を決定するフローを導入。
3. **テスト更新**: ツール変更に合わせて `test_create_knowledge_base.py` のアサーションを緩和。

## 解決策の詳細
- `src/ragmaker/tools/create_knowledge_base.py`:
  - `create_knowledge_base` 関数内の `categories` ループを削除。
- `.gemini/commands/rag.md`:
  - ステップ3「ナレッジベースの最終配置」を、ベースパス選択、プロジェクト名決定、最終パス確定、の3段階に分割。
